# 坑槽照片标注复核 API

质检员汇总多人标注后，用本服务复核未确认照片。基于 Dawid–Skene 模型
（FastAPI + NumPy）估计每名标注员的误标率/漏标率，并对每张未确认照片
给出有坑概率；无票可用时标为“待人工复核”。

## 方法

**模型假设**

- 类别：0 = 无坑，1 = 有坑；类别先验固定为各 0.5。
- 每名标注员一个 2×2 混淆矩阵 `conf[c][k] = P(投票 k | 真实类别 c)`，
  M 步加一平滑：
  - 误标率 = `conf[0][1]`（无坑被投成有坑）
  - 漏标率 = `conf[1][0]`（有坑被投成无坑）
- 专家标签固定：E 步后专家照片的后验重置为 one-hot，不再更新。
- 缺票不计：只对实际存在的投票累加，不为缺失投票补默认值。

**逐张复核（留一法）**

评估每张未确认照片时：

1. 从拟合数据中移除该照片及其全部投票；
2. 按剩余投票把相连的照片和标注员做并查集分组；
3. 每个**同时含正、负专家标签**的组单独做 EM 拟合（其余组不拟合）；
4. 只用已收敛组中标注员投给该照片的票，按贝叶斯公式（先验各半）
   计算有坑概率；
5. 无票可用 → `pending_manual_review`（待人工复核）。

**慢收敛票表的补算（两个接口共用同一规则）**

- 收敛精度：混淆矩阵相邻两轮最大绝对变化 `< 1e-9`（原精度）。
- 每组先按原上限独立拟合**至多 200 轮**。
- 每个请求另有 **200 轮补算额度**，由该请求中“相关未收敛组”共用；
  采用逐轮轮转推进，额度分配确定、可复现。
- `/review`：逐张处理，只有**投过当前待判照片**（按留一后分组）的未收敛
  组才可动用补算额度；每次按该照片留一后各组的收敛状态选票——已收敛组
  的票照常用于打分，仍未收敛组的票计入 `votes_ignored`；全部票都不可用
  时转人工复核。
- `/annotator-stats`：在完整数据上分组，所有未收敛组合用同一份 200 轮
  额度；仍未收敛的组标为 `not_fitted`，`note` 说明原因（已跑轮数、
  最近两轮最大变化）。
- 每个请求内部状态独立、遍历顺序固定，因此同一份请求重复调用结果一致。

## 快速开始

### Docker Compose（推荐）

```bash
docker compose up --build
```

`review-api` 服务监听 `http://127.0.0.1:8000`，交互式文档见 `/docs`。
`demo` 容器在服务健康后自动调用两个接口并打印结果，随后退出；
可用 `docker compose logs demo` 查看。演示只读挂载 `./demo`，可改
`demo/payload.json` 后重跑 `docker compose run --rm demo`。

### 本地运行

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000
```

### 演示请求

```bash
python3 demo/demo.py            # 读取 demo/payload.json，调用 /review 与 /annotator-stats
# 或手动：
curl -X POST http://127.0.0.1:8000/review \
  -H 'Content-Type: application/json' \
  -d @demo/payload.json
```

`demo/payload.json` 含三张票表，覆盖三种收敛情形：

| 组 | 数据特征 | 演示的现象 |
| --- | --- | --- |
| A 组（a1–a3） | 原 200 轮内收敛 | 正常评分 |
| B 组（b1–b3） | 完整数据需 253 轮 | 动用共享补算额度收敛后评分（`T1` 同时用到 A、B 两组） |
| C 组（c1–c3） | 完整数据需 1327 轮 | 留一后部分照片可在 200 轮内收敛；`C7` 需再补 167 轮，但额度只剩 147 轮 → 待人工复核、忽略 3 票；`U1` 所在完整组始终未收敛 → 待人工复核、忽略 1 票；`/annotator-stats` 对 C 组标为 `not_fitted` |

`T1` 展示跨组选票，`U1` 展示只含未收敛组投票的照片，`V1` 展示留一后
无组可用的标注员，`P0` 展示完全无票的照片。

## API

### `POST /review`

请求体（`demo/payload.json` 为完整示例）：

| 字段 | 说明 |
| --- | --- |
| `photos` | 照片编号列表，1–80 个，不可重复 |
| `annotators` | 标注员编号列表，1–12 个，不可重复 |
| `votes` | 投票记录 `[{photo, annotator, label}]`，`label`：1=有坑，0=无坑；缺票即不出现；同一照片同一标注员只能投一票 |
| `expert_labels` | 专家标签 `[{photo, label}]`，拟合中固定 |

响应：

- `confirmed`：专家已确认的照片（不参与复核）；
- `results`：每张未确认照片的复核结论：
  - `status: "scored"` → `pothole_probability`（有坑概率）与
    `votes_used`（每票的标注员及其误标率/漏标率）；
  - `status: "pending_manual_review"` → 无票可用，待人工复核；`note`
    说明原因（无投票 / 标注员不在任何组 / 组缺专家标签 / 组未收敛）；
  - `votes_ignored`：未采用的票数（标注员不在任何组、所在组缺专家标签、
    或所在组在原 200 轮与共享补算额度内仍未收敛）。

### `POST /annotator-stats`

请求体同上。在完整数据上按同样规则分组拟合，汇总每名标注员的
误标率/漏标率；所在组缺少正或负专家标签、无投票，或所在组在原 200 轮
与共享 200 轮补算后仍未收敛的标注员标为 `not_fitted`，`note` 说明原因。

### `GET /health`

健康检查，返回 `{"status": "ok"}`。

## 设计说明与限制

- 组内要求**正负专家标签齐全**是为了锚定两个类别，避免 EM 的标签
  交换不可辨识问题；不满足的组不拟合，其中标注员的票不用于复核。
- 每张未确认照片独立做一次留一拟合，因此同一标注员在不同照片的
  结果里误标/漏标率可能略有差异；汇总视图请用 `/annotator-stats`。
- 补算额度按请求计算、不跨请求累计；`/review` 按 `photos` 顺序逐张
  消耗，先处理的照片先占用额度，因此照片顺序会影响哪些组能用完补算。
  这是“同一份请求结果一致”的直接代价；如需与顺序无关，应改为按张
  独立额度（会改变题意）或固定额度分配策略。
- 规模为 ≤80 张照片、≤12 名标注员；`/review` 每张照片先做一次分组拟合
  （每组 ≤200 轮），全请求补算合计 ≤200 轮。最坏情况（80 张、单一大组）
  实测约 5–10 秒；正常请求在毫秒级到秒级。
- 结果为有坑概率，是否判为坑槽的阈值（如 0.5）由业务方决定，
  服务不代为下结论。
